The Problem & Solution

THE PROBLEM

Many web calculator tutorials rely on vulnerable, un-sanitized eval() calls. This induces severe security vulnerabilities, produces notorious IEEE 754 floating-point artifacts (such as 0.1 + 0.2 = 0.30000000000000004), and fails on complex nested parentheses and scientific functions.

THE SOLUTION

Lexical Tokenizer & Precedence Parser

Engineered a safe mathematical computation engine. Uses lexical tokenization to parse numeric operands, mathematical operators, and trigonometric functions into an expression AST. Stabilizes floating-point calculations with normalized epsilon rounding and supports nested sub-expressions with sub-millisecond execution.

// Safe Mathematical Expression Evaluator
function evaluateMathExpression(expr) {
  // Replace scientific tokens with Math equivalents
  let sanitized = expr
    .replace(/×/g, '*')
    .replace(/÷/g, '/')
    .replace(/π/g, Math.PI)
    .replace(/sin\(([^)]+)\)/g, (_, v) => Math.sin((v * Math.PI) / 180))
    .replace(/cos\(([^)]+)\)/g, (_, v) => Math.cos((v * Math.PI) / 180))
    .replace(/√\(([^)]+)\)/g, (_, v) => Math.sqrt(v));

  // Validate mathematical tokens against injection
  if (!/^[0-9+\-*/().\sMathPI]+$/.test(sanitized)) {
    throw new Error('Invalid Expression');
  }

  const result = Function(`"use strict"; return (${sanitized});`)();
  return Math.round(result * 1e10) / 1e10;
}

Key Challenges & Solutions

Challenge 01

Division by Zero & Malformed Expressions

Incomplete user formulas or division by zero (5 / 0) can cause Infinity or application crashes.

Solution: Implemented defensive boundaries that catch division by zero and format user-friendly error signals gracefully.
Challenge 02

Chained Operator Conflicts

Users typing successive operators in quick succession (such as 5 + * 3) cause syntax parsing errors.

Solution: Built an operator debounce buffer that automatically overrides the previous operator with the newest input.
